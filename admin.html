Option 1: Browser extension Recommended · No command line · All platforms

Use a small browser extension to sync the muse.ai login session already signed in on your own computer. No need to install Python, open a terminal, or type commands.
Why an extension is required: muse.ai's login session cookies carry the httpOnly flag, so page scripts (document.cookie typed in F12, bookmarklets) cannot read them; only a browser extension's cookies API can.
1
Download and unzip the extension
Unzip it into a directory you won't delete, e.g. D:\muse2api-extension.
⬇ Download muse2api-extension.zip
2
Load the extension in your browser
Using Chrome as an example (Edge / Brave / 360 and other Chromium-based browsers are similar):
  1. Type chrome://extensions in the address bar and press Enter
  2. Turn on the Developer mode switch in the top-right corner
  3. Click Load unpacked in the top-left corner
  4. Select the folder you unzipped in step 1 (not a single file inside it)
3
Log in to muse.ai, then click the extension icon to import
First open https://muse.ai/ in your own browser and sign in (until you can see the chat interface), then click the extension icon in the browser toolbar, fill in the two fields below, and click "Read and import".

Option 2: Copy manually No install · Fallback

If you don't want to install the extension, you can manually extract the cookie string. The key is to use the request headers in the "Network" panel, not the Console — the cookie: line in the request headers includes the httpOnly cookies, which the Console cannot read.
  1. Open and sign in to https://muse.ai/ in your own browser, and stay on the chat interface
  2. Press F12 to open DevTools and switch to the Network panel
  3. Press F5 to refresh the page so the request list populates
  4. Click any muse.ai request in the list (the first one is fine)
  5. On the right, find Headers → scroll down to Request Headers
  6. Find the line starting with cookie: and copy the whole string after the colon
    7. (starting from hatch_sess=, all the way to the end of the line)
  7. Paste it into the input box under "Method 3" and click Import
Note: use the cookie: in the request headers, not the "response headers". The set-cookie in the response headers only contains some of the cookies and will be missing some.

Integration guide

The endpoints align with OpenAI style — downstream projects only need to change base_url and api_key.
BASE URL:—

1. Available models

Model IDUseEndpoint
muse-sparkText / code chat (streaming supported)POST /v1/chat/completions
POST /v1/responses
muse-imageText-to-image / image editingPOST /v1/images/generations
muse-videoText-to-video / image-to-videoPOST /v1/videos → GET /v1/videos/{id}
These three are the real capabilities of the Muse family: Muse Spark (language / code), Muse Image (image generation), Muse Video (video generation). The muse.ai web page routes automatically via its agent and has no model picker, so the model field is only for downstream compatibility — passing common names such as gpt-4o, claude-sonnet-4, dall-e-3, etc. automatically maps them to the matching capability.

2. Chat / coding

Copy# Non-streaming
curl -X POST "BASE/v1/chat/completions" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-spark","messages":[{"role":"user","content":"Write a Python quicksort"}]}'

# Streaming: add "stream":true; returns standard SSE (data: {...} / data: [DONE])

3. Image generation (curl)

Copycurl -X POST "BASE/v1/images/generations" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"A Shiba Inu wearing an astronaut helmet","size":"1:1","response_format":"url"}'

# Response
{"created":1790148495,"data":[{
  "revised_prompt":"A Shiba Inu wearing an astronaut helmet",
  "url":"http://your-server:18610/v1/media/xxxx.webp",
  "kind":"image","bytes":23860}]}

# url is a full absolute address that downstream apps can render / download directly; /v1/media/* needs no auth.
# For base64, pass "response_format":"b64_json".

4. Video generation (curl, async)

Copy# ① Create the task
curl -X POST "BASE/v1/videos" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"A kitten walking on the grass","duration":5,"size":"16:9"}'
# → {"id":"task_xxx","status":"queued"}

# ② Poll for the result
curl "BASE/v1/videos/task_xxx" -H "Authorization: Bearer $MUSE2API_KEY"
# → {"status":"succeeded","result":{"url":"/v1/media/xxx.mp4"}}

5. Python (openai SDK compatible)

Copyfrom openai import OpenAI
import time

client = OpenAI(base_url="BASE/v1", api_key="m2a_...")

# Image generation
r = client.images.generate(model="muse-image", prompt="A Shiba Inu wearing an astronaut helmet")
print(r.data[0].url)

# Video generation (uses the native endpoint because it is asynchronous)
import requests
t = requests.post("BASE/v1/videos", json={"prompt":"A kitten walking","duration":5},
                  headers={"Authorization":"Bearer m2a_..."}).json()
while True:
    s = requests.get(f"BASE/v1/videos/{t['id']}",
                     headers={"Authorization":"Bearer m2a_..."}).json()
    if s["status"] in ("succeeded","failed"): break
    time.sleep(5)
print(s)

7. Authentication

All endpoints except /healthz, /readyz, and /v1/media/* require Authorization: Bearer <API Key>. The API Key is configured on the server in /opt/muse2api/.env under MUSE2API_KEY.

8. Connecting clients / agents

Any client that supports a \"custom OpenAI-compatible endpoint\" works with just three values:
SettingValue
Base URL / API addresshttp://<your server IP or domain>:18610/v1
API Keym2a_... (the one under \"Connection info\" at the top of this page)
Model namemuse-spark
Any model name works: common names (gpt-4o, gpt-5, claude-sonnet-4, deepseek-chat, gemini-2.5-pro, etc.) are automatically mapped to the matching capability; a completely unfamiliar name is passed through as-is, and since muse.ai routes automatically anyway, it doesn't affect the result.

About the "tool calls" limitation (important, measured):
The muse.ai web assistant has an explicit alignment refusal policy against "outputting fake tool-call JSON" — the measured reply is "I won't output 'fake tool calls' in this JSON format — I don't have a get_weather tool". We tried three different prompt protocols with different wording and placements, and all of them failed.
So: autonomous agent mode that depends on tool_calls (automatically reading/writing files, running commands, etc.) won't work; but all Q&A-style uses — chatting, writing code, explaining, translating, summarizing, generating images, generating videos — are fully supported.
If a client forcibly includes the tools field, the endpoint won't return an error; it will ignore the tool declarations and answer as a normal chat.

Account proxy

The account's browser, session checks and keep-alive use the same proxy. A proxy failure is reported without falling back to a direct connection.

Paste an HTTP, SOCKS5 or SOCKS5h URL including credentials and test it immediately, without saving.

Enter credentials manually (optional)

The saved password is never shown. Leave it blank to keep it when the server and username are unchanged; enter it again after changing either.

Wait for the account's active task to finish before editing its proxy. Saved changes apply to the next request.
